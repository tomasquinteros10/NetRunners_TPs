    \begin{enumerate}
        \item El usuario TS emisor ya conoce la dirección del usuario destino.
        
      \item Utilizar direcciones conocidas para servicios comunes.

    \end{enumerate}
  \item 
  \textbf{Explique el uso de la multiplexación en el contexto de un protocolo de transporte.}

    La \textbf{multiplexación} permite que el protocolo de transporte utilice de manera más eficiente las conexiones de red. La idea es que varias conexiones de transporte puedan compartir una misma conexión de red, o que una conexión de transporte pueda utilizar varias conexiones de red.

    Se pueden distinguir dos casos:

    \begin{itemize}
    \item \textbf{Multiplexación hacia arriba (upward multiplexing):} varias conexiones de transporte utilizan una única conexión de red. Esto permite reducir la cantidad de conexiones de red necesarias, compartiendo una misma conexión entre diferentes conexiones de transporte.

    ```
    \item \textbf{Multiplexación hacia abajo (downward multiplexing):} una única conexión de transporte utiliza varias conexiones de red. Los datos pueden distribuirse entre estas conexiones, lo que permite aprovecharlas simultáneamente y puede mejorar el rendimiento.
    ```

    \end{itemize}

    En resumen la multiplexación permite aprovechar mejor los recursos de la red, ya sea haciendo que varias conexiones de transporte compartan una misma conexión de red, o utilizando varias conexiones de red para una misma conexión de transporte.

  \item
    \textbf{Describa brevemente el esquema de créditos utilizado por TCP para el control de flujo.}

    TCP utiliza un \textbf{esquema de créditos} para realizar el control de flujo y evitar que el emisor envíe más datos de los que el receptor puede almacenar.

    Cada octeto de datos posee un número de secuencia, y los segmentos TCP incluyen un número de secuencia, un número de confirmación (\textit{ACK}) y un tamaño de ventana. El receptor utiliza la ventana para indicar al emisor cuántos octetos adicionales está preparado para recibir.

    Por ejemplo, si un ACK contiene \(AN=i\) y una ventana \(W=j\), significa que todos los octetos anteriores a \(i\) fueron recibidos correctamente, que se espera recibir el octeto \(i\) y que el emisor tiene permiso para enviar hasta \(j\) octetos adicionales.

    De esta manera, el receptor puede informar dinámicamente cuánto espacio disponible tiene en su buffer. Si la ventana es pequeña, el emisor debe reducir la cantidad de datos que envía; si aumenta, puede enviar más datos.

    Una característica importante del esquema de créditos de TCP es que \textbf{el control de flujo está desacoplado de las confirmaciones}. Es decir, un segmento puede confirmar datos recibidos sin necesariamente otorgar nuevos créditos, o puede otorgar créditos sin confirmar nuevos datos.

  \item \textbf{¿Cuál es la diferencia principal entre el esquema de créditos de TCP y el esquema de control de flujo de ventana deslizante utilizada por muchos otros protocolos, como por ejemplo HDLC?}

  En el esquema de ventana deslizante, la confirmación o ACK de la llegada de datos habilita al emisor inmediatamente a enviar más datos. En cambio, en el sistema de créditos se puede dar el ACK de que los datos llegaron, pero la habilitación para enviar más datos es independiente. Por lo tanto, el emisor puede recibir la confirmación de la llegada de los datos, pero no tener permitido enviar más hasta recibir créditos adicionales para continuar la comunicación.

  \item \textbf{Explique los mecanismos de diálogo en dos y tres pasos.}

  En un diálogo en dos pasos entre dos interlocutores A y B, A inicia la solicitud de conexión con un mensaje SYN i. B responderá con un SYN j y confirmará la recepción del SYN de A con un ACK (i + 1). En el diálogo de tres pasos, A enviará un SYN i, B lo recibe y responde con SYN j y ACK (i + 1). Cuando A recibe el SYN de B, responde con ACK (j + 1). Los valores i y j serán números de secuencia elegidos de forma independiente por cada uno de los interlocutores.

  \item \textbf{¿Cuál es el beneficio del mecanismo de diálogo en tres pasos?}
  
  El establecimiento de una conexión debe tener en cuenta la falta de fiabilidad del servicio de red. Si A envía un SYN a B, pueden ocurrir dos problemas:
  \begin{enumerate}
    \item Que se pierda el SYN de A o 
    \item Que se pierda la respuesta de B
  \end{enumerate}
  Esto se puede resolver retransmitiendo SYN. Sin embargo puede generar duplicados. Por ejemplo, si la respuesta de B solamente estaba retrasada, A enviara otra solicitud que B ya recibió.

  
  También pueden quedar segmentos de datos viejos. Si una nueva conexión utiliza los mismos números de secuencia que una anterior, estos segmentos podrían confundirse. Cada conexión debe comenzar con un numero de secuencia diferente al anterior.


  También un SYN viejo puede llegar después del cierre de una conexión y ser interpretado como una solicitud nueva y es conectan aunque estén esperando números de secuencia distintos.
  Esto se resuelve con el dialogo en tres pasos:
  \begin{enumerate}
    \item A envía un SYN on numero de secuencia inicial.
    \item B confirma el SYN de A y envía su propio SYN con numero de secuencia inicial propio.
    \item A confirma el SYN de B.
  \end{enumerate}
  El beneficio es que cada extremo confirma explícitamente el SYN y numero de secuencia inicial del otro antes de considerarse establecida la conexión. De esta manera evita conexiones incorrectas por la solicitud vieja o duplicada y se asegura sobre los números de secuencia que van a utilizar
  \item \textbf{Defina las características de urgencia y forzado de TCP.}

  TCP almacena temporalmente los datos tanto al enviarlos como al recibirlos. Normalmente, decide cuándo formar un segmento para transmitirlo y cuándo entregar los datos recibidos a la aplicación. Además, ofrece dos servicios útiles para etiquetar los datos: forzado y urgente.

  \begin{itemize}
      \item \textbf{Flujo de datos forzados:} permite solicitar que TCP envíe los datos pendientes sin esperar a acumular más. En el extremo receptor, indica que los datos deben entregarse a la aplicación sin seguir reteniéndose a la espera de más datos. Esto resulta útil cuando se termina una parte lógica de la información y se necesita que el receptor pueda procesarla.

      \item \textbf{Señalización de datos urgentes:} permite avisar a la aplicación receptora que hay datos que requieren atención especial. TCP utiliza un puntero de urgente para señalar el final del bloque de datos urgentes. Estos se transmiten dentro del flujo de datos normal. La aplicación receptora es responsable de decidir qué acción realizar.
  \end{itemize}
  
  En la cabecera TCP se encuentran los indicadores correspondientes de 6 bits:
  \begin{itemize}
      \item \textbf{PSH:} señala la función de forzado.
      \item \textbf{URG:} indica que el campo de puntero urgente es válido.
  \end{itemize}

  La diferencia es que el forzado busca evitar la espera por acumulación de datos, mientras que la urgencia señala que una parte de los datos requiere atención especial.

  \item 
  \textbf{¿Qué es una opción en los criterios de implementación de TCP?}

  El estándar de TCP (RFC 793) especifica el formato de los segmentos y las reglas del protocolo, pero deja libertad en algunos aspectos de implementación: aunque dos TCP elijan opciones distintas, el protocolo sigue funcionando igual, pero el rendimiento puede variar según qué política haya elegido cada uno. Podemos nombrar cinco áreas (las más importantes):
\begin{itemize}
      \item \textbf{Política de envío:} cuándo el emisor arma un segmento con los datos que tiene acumulados (enviar apenas tenga algo disponible, o esperar a juntar más datos antes de armar el segmento).
      \item \textbf{Política de entrega:} lo mismo que en la de envío, pero del lado del receptor (entregar los datos a la aplicación apenas llega cada segmento en orden, o acumular varios segmentos antes de entregarlos).
      \item \textbf{Política de aceptación:} qué hacer si llegan segmentos desordenados (aceptar lo que llega en secuencia y descartar el resto, o aceptar y guardar cualquier segmento que caiga dentro de la ventana de recepción aunque esté desordenado).
      \item \textbf{Política de retransmisión:} qué hacer cuando vence el temporizador de un segmento no confirmado.
      \item \textbf{Política de confirmación:} cuando llega un segmento en orden, se confirma al instante de la llegada o se espera a pisar la confirmación sobre el próximo.
  \end{itemize}
  
  \item 
   \textbf{¿Cómo puede utilizarse TCP para tratar la congestión de red o de interconexión de red?}

TCP controla la congestión de forma indirecta, ya que no puede controlar directamente los elementos de la red. Detecta posibles situaciones de congestión a partir de la \textbf{pérdida de paquetes, ACKs duplicados o aumentos en los tiempos de espera}. Para regular la cantidad de datos que transmite, utiliza principalmente los siguientes mecanismos:

\begin{itemize}
    \item \textbf{Ventana de congestión (\(CWND\))}: limita la cantidad de datos que pueden encontrarse en tránsito. La cantidad efectiva de datos enviados está limitada por el mínimo entre \(CWND\) y la ventana anunciada por el receptor (\(RWIN\)).

    \item \textbf{Arranque lento (Slow Start)}: al comenzar una conexión o después de una congestión importante, TCP inicia con una ventana pequeña y aumenta rápidamente \(CWND\), buscando determinar progresivamente la capacidad disponible de la red.

    \item \textbf{Evitación de congestión (Congestion Avoidance)}: cuando \(CWND\) alcanza el umbral \(ssthresh\), su crecimiento se vuelve más lento y aproximadamente lineal, evitando sobrecargar la red.

    \item \textbf{Retransmisión rápida y recuperación rápida (Fast Retransmit / Fast Recovery)}: cuando TCP recibe varios ACKs duplicados, interpreta que probablemente se perdió un segmento. Lo retransmite sin esperar a que expire el temporizador y reduce la ventana de congestión para disminuir la carga sobre la red.

    \item \textbf{Temporizador de retransmisión (RTO)}: TCP adapta el tiempo de espera para las retransmisiones en función de las estimaciones del RTT. Si aumenta el retardo de la red, el RTO se ajusta para evitar retransmisiones prematuras que podrían aumentar aún más la congestión.
\end{itemize}

En conjunto, estos mecanismos permiten que TCP \textbf{adapte dinámicamente la velocidad de transmisión a las condiciones de la red}, reduciendo el tráfico cuando detecta congestión y aumentando progresivamente la transmisión cuando la red parece tener capacidad disponible.
  
  \item 
    \textbf{¿Qué proporciona UDP que no ofrezca IP?}

    
    El Protocolo de Datagramas de Usuario UDP (User Datagram Protocol) es un protocolo de la capa de transporte orientado a no conexión que ofrece un servicio de entrega de mensajes no confiable y de mínimo esfuerzo sobre la capa de red.
    
    Específicamente, UDP añade sobre el servicio básico de IP dos funciones fundamentales de la capa de transporte:
\begin{itemize}
     \item \textbf {Puertos de origen y destino:} Permite la multiplexación y desmultiplexación del tráfico, entregando los datos a un proceso o aplicación específica dentro del equipo de destino, a diferencia de IP que solo entrega el paquete de equipo a equipo.
    
     \item \textbf {Suma de comprobación (Checksum):} Ofrece una verificación de errores de extremo a extremo que protege tanto la cabecera UDP como la carga útil de datos y una pseudo-cabecera IP, asegurando que el mensaje no haya sufrido corrupción en el trayecto. En IPv6, este mecanismo es obligatorio.
\end{itemize}
